# 0.2.4 — silent in-app navigation and repository updates

## Use navigation

1. Install the new APK **over** the existing app, retaining its package/signing identity and all app storage. Do not uninstall. Trail database schema remains version 2; no migration, deletion, or rewrite is introduced.
2. Tap **Navigate**, enter a place name or `latitude, longitude`, explicitly search and choose a result. Alternatively hold a location on the map and select **Preview in oTraiL**.
3. A recent, reasonably accurate GPS fix is required as the starting point. If necessary tap Locate and wait for reception. Destinations are limited approximately to India.
4. Review the blue route, total driving distance and duration, then tap **Start**. The panel shows written maneuvers, distance to the next instruction, remaining distance and approximate remaining time. There is **no voice guidance**, speech engine or sound alert.
5. Recenter resumes following the live GPS dot after panning. Turns opens the complete maneuver list. Clear ends navigation and clears the route cache; GPS journaling keeps running.

The default route provider is the FOSSGIS public OSRM car endpoint. It is suitable for light personal use and has no availability guarantee or live traffic. Request origin/destination are sent to the selected routing server. Search uses Android's geocoder, which may be absent or network-dependent; map-point and coordinate entry are alternatives. Maps & downloads allows a replacement HTTPS OSRM driving endpoint.

Sources: [OSRM API](https://project-osrm.org/docs/v5.24.0/api/), [FOSSGIS routing usage/privacy](https://routing.openstreetmap.de/about.html). The app identifies itself, displays routing attribution, links to map corrections, spaces manual requests by at least two seconds and automatic reroutes by at least 60 seconds.

## Guidance, offline behavior and data integrity

- Navigation geometry/steps are derived data in `navigation-route.json`, written atomically on a separate worker. They are never appended to `fixes`, substituted for measurements, or mixed into stop/GeoJSON exports.
- GPS recording stays on its existing dedicated writer. Navigation receives a copy after the real fix is committed. Guidance calculation, route HTTP requests and cache writes use independent workers.
- Fresh GPS fixes update route progress. Inaccurate and duplicate fixes are ignored for navigation. Rerouting requires three accurate off-route observations and a cooldown. Arrival requires repeated good fixes near the route end and proximity to the requested target.
- A failed reroute keeps the cached route; a failed replacement preview retains the previous route/target consistently. The user sees the failure. Stale GPS is shown rather than pretending current guidance.
- Active/preview routes restore from cache across app/process/reboot restarts. Offline-only blocks new route calculations and reroutes. The existing cached geometry and turn list can still be followed with GPS.
- This is **not a full offline routing engine**. It cannot calculate a new path when disconnected. Existing `.map` files render maps, while `.osm.pbf` is raw source data; neither is directly a navigable graph here.
- Full collected trails, stop enrichment, inferred-gap logs, map downloads and trail backups remain separate. There is no database-version change for this release.

## Daily and manual GitHub updates

Maps & downloads → **App updates · daily / check now** enables/disables daily checks and provides Check now. Daily checks are enabled by default, network-constrained, persisted with Android JobScheduler and quiet when there is no newer version. Android may defer periodic jobs; it is not an exact wall-clock alarm. Newer versions produce one notification per version when notification permission is granted. Background checks never download/install an APK silently.

The update source is `https://raw.githubusercontent.com/viskie/oTrail0/main/releases/latest.json`. No GitHub Releases API, account token, or GitHub Release publishing workflow is used.

The manifest contains:

```json
{
  "versionCode": 6,
  "versionName": "0.2.4",
  "apkUrl": "https://raw.githubusercontent.com/viskie/oTrail0/main/releases/oTraiL-0.2.4-debug.apk",
  "sha256": "<generated from the exact APK>",
  "sizeBytes": 0,
  "notes": "Release notes"
}
```

The example digest/size above are illustrative; the actual committed manifest has the real values. For every future APK:

1. Increment Android versionCode/versionName and build with the **same signing key**.
2. Commit the APK in `releases/`.
3. Generate its SHA-256 and size and update `releases/latest.json` and `releases/SHA256SUMS` in the same commit.
4. Push to main; the next daily or manual check can see it. Raw GitHub responses may be cached briefly.

The app accepts only HTTPS artifact URLs in this repository's releases directory, enforces a size limit and checks the full SHA-256. Before sharing a private read-only APK URI with Android's installer it verifies package name, exact advertised version, strictly higher versionCode and the same APK signing certificate set as the installed app. Failed candidates are not installed. The verified artifact is separate from journals and map storage. No uninstall/data-clear operation exists in this updater.

The first install may require **Allow from this source** for oTraiL. Android still requires the user's install confirmation; ordinary apps cannot silently replace themselves. See [Android install-source permission](https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls()). Debug signing is still for personal testing; preserve the signing identity for future updates.

## Validation for this release

- 29 JVM tests: existing stop, geometry and heritage tests plus route parsing, written maneuvers, progress/arrival, off-route confirmation, duplicate/poor-accuracy rejection, loop handling, immutable geometry and update-manifest restrictions/version comparisons.
- Android lint and debug app/test APK compilation.
- A live synthetic Delhi routing request returned 244 geometry points and 20 maneuvers; the app's production parser read it successfully.
- An additional device instrumentation check compares journal snapshots before/after cached-navigation operations. It is compiled here, **not executed for 0.2.4**, because the phone is unavailable; the requested delivery is an APK upload to GitHub. Phone UI, actual driving, and the Android installer flow still need device testing.
- Previous 0.2.3 device checks are not presented as new 0.2.4 device validation.

## Suggested offline routing techniques (next phase)

1. **Route caching — implemented now.** Cache a planned route and its instructions. This covers loss of connectivity while staying on that route, but cannot calculate detours.
2. **BRouter on-device graph tiles.** BRouter provides Java/Android offline routing and 5×5-degree `.rd5` graph segments, with configurable profiles including car routing. A regional tile downloader plus an adapter to `RoutePlan` would enable local recalculation. Validate car profiles and maneuver quality against your India journeys. This is the most direct Android-oriented candidate to prototype. [BRouter project and data layout](https://github.com/abrensch/brouter).
3. **Native Valhalla with regional routing tiles.** A longer-term option for a dedicated car-navigation pipeline: build regional graph packs from OSM extracts off-device, deliver versioned tiles to the phone, and connect a native Android/JNI engine to the same guidance model. This requires more native build/distribution work; it is not shipped in 0.2.4. [Valhalla](https://github.com/valhalla/valhalla), [tiled graph design](https://valhalla.github.io/valhalla/concepts/tiles/).

For either graph engine, start with the states/corridors you drive, include boundary overlap, keep graph data out of the APK/repository, and use manual phone downloads with size/progress/checksum/rollback support. Route graphs and recorded GPS trails must remain separate datasets.
